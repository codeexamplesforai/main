## 0. WHO YOU ARE, WHAT YOU'RE BUILDING, AND THE ABSOLUTE OUTPUT RULES

You are a senior frontend engineer who builds polished, dense, "looks like a real product" enterprise dashboards. You are going to produce **ONE SINGLE `.html` file** that contains a fully self-contained, interactive demo of an anti-money-laundering (AML) detection platform called **AML Framework / Feature Factory**.

### Absolute output rules — DO NOT VIOLATE

1. **One file only.** Output exactly one HTML document. No external JS files, no external CSS files, no images on disk.
2. **No build step.** It must run by simply double-clicking the `.html` file in a browser. No npm, no vite, no bundler.
3. **External CDNs allowed (only these three):**
   - Tailwind CSS Play CDN: `https://cdn.tailwindcss.com`
   - Lucide icons CDN: `https://unpkg.com/lucide@latest`
   - Optional: Chart.js from `https://cdn.jsdelivr.net/npm/chart.js` ONLY if you choose to use it for histograms. Hand-written SVG is preferred and equally acceptable.
4. **No backend, no `fetch()` to real APIs.** Everything is driven by hardcoded JSON arrays in a single `<script>` tag near the top.
5. **No frameworks.** No React, no Vue, no Alpine. Use plain vanilla JavaScript, `querySelector`, `addEventListener`, and template strings + `replaceChildren` / `insertAdjacentHTML('beforeend', ...)` to render. (You may use Tailwind's class-based utility CSS, which the CDN compiles at runtime.) Treat all your own template strings as trusted — there is no user-supplied HTML in this demo. When you do inject markup, prefer `insertAdjacentHTML` and `Element.replaceChildren(...)` so the code stays explicit and reviewable.
6. **Dark theme only.** This is a dense, navy/black dashboard. Never light mode.
7. **It must actually work.** Every button labelled in the spec must do something visible — open a modal, toggle a panel, filter a table, switch a tab, run a fake "pipeline" with a streaming console, etc. Inert decorative buttons are not acceptable.
8. **Demo data is static but realistic.** Use believable entity IDs, dates near 2026-05-19, dollar amounts, country codes, etc. Aim for at least 20 alerts, 15 feature blocks, 12 risk typologies, 30 entities, 8 GTM rows, 5 execution history rows, etc. Real-looking, not `foo/bar`.
9. **Performance budget.** The whole file should be under ~250 KB. Use compact JSON. Don't dump 10,000 row datasets — paginate or truncate with realistic counts.
10. **Accessibility basics.** Buttons are `<button>`, links are `<a>`, headings hierarchical (one `<h1>` per page), focus rings visible.

If you cannot satisfy any rule above, **say so explicitly at the top of your answer and then continue building**. Do not silently drop features.

## 1. WHAT THE PRODUCT IS (so you can populate it convincingly)

This is an internal-tooling SPA used by a bank's financial-crime / AML team. It has TWO sections joined by one sidebar:

- **Layer 1 · Feature Factory** — engineers build, validate, and execute "feature blocks" (Python-ish code that computes risk features from raw transaction / account / client data).
- **Detection Framework (Layers 2–5)** — analysts and investigators run a 5-layer pipeline that turns features into model signals → aggregated risk profiles → escalation decisions → packaged alerts → assigned cases with disposition.

Think Palantir Foundry meets a real bank's transaction-monitoring system. Dense, technical, lots of tables and JSON, but legible.

The full 5-layer pipeline:
1. **L1 — Feature Factory** (compute features from raw data)
2. **L2 — Model Layer** (rule-based / hybrid / unsupervised models produce signals)
3. **L3 — Signal Aggregator** (combine signals per entity, ATL/BTL classification)
4. **L4 — Risk Appetite** (escalation rules decide TRACK_A auto-alert, TRACK_B classifier, TRACK_B_LLM uncertain)
5. **L5 — Alerts** (packaged alert objects with 3-level depth: entity → targeted risks → occurrences)

Acronyms users will see — use them verbatim:
- **ATL** = Above-the-Line (high-confidence targeted hit)
- **BTL** = Below-the-Line (anomaly / unsupervised hit)
- **RT** = Risk Typology, e.g. `RT_VELOCITY`, `RT_GEOGRAPHIC`, `RT_CASH`
- **GTM** = Global Tuning Matrix (per-RT per-country thresholds)
- **FATF** = Financial Action Task Force (categorises risk typologies)

## 12. ANTI-TEMPLATE / QUALITY BAR

Do not ship the demo looking like a generic Tailwind starter. Specifically:
- Use **typographic hierarchy**: page title is text-2xl bold, section headings text-sm uppercase tracking-wider navy-400, KPI values text-2xl mono.
- Use **density**: a real product has 4–6 elements per row on a wide screen, not 2 giant cards with 200 px padding.
- Use **mono everywhere data feels code-ish**: entity keys, IDs, timestamps, scores, JSON, country codes, currency codes.
- Use **subtle layering**: cards have 1 px navy-600 border AND a faint shadow on hover. Headers within cards have a bottom hairline (`border-b border-navy-600/60 pb-3 mb-3`).
- Use **semantic colors only where they mean something** — don't randomly tint things violet because it looks nice. Violet means L2 / CLIENT category. That's it.
- Avoid uniform spacing — section labels are tight, body content is breathy, hierarchy through scale not just bold.

If a section feels empty, add a small inline helper text or a 2-row mini table. Do not leave 600 px of blank space anywhere.
